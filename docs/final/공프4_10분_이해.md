# 공프4 기말 — 10분 만에 이해하기

발표 전에 한 번 읽으면 질문에 답할 수 있도록, 기말에서 무엇을 했고 무엇이 나왔는지를 순서대로 정리했습니다.

## 1분: 한 문장 요약

**현장 실적이 들어오면 출하검사에 늦을지 예측하고, 늦을 것 같으면 순서를 바꾼 계획(필요하면 추가근무 포함)을 제안하며, 관리자가 승인한 계획이 다시 현장 작업지시로 내려가는 시스템을 만들고, 이를 가상 현장에서 810번 돌려 효과를 확인했다.**

## 2분: 중간발표에서 무엇이 바뀌었나

| 중간발표 | 기말 |
|---|---|
| 실적 입력 → Forecast → 긴급 판정 → 후보 비교 → 승인까지 **화면에서** 보여 줌 | 승인한 계획이 **작업지시 API(/work-orders)**로 현장에 내려감 (폐루프) |
| 시연 1개 시나리오 | **810회 반복 실험** (3조건 × 9구성 × 30 seed) |
| 4개 순서 규칙(FCFS·EDD·Slack·CR)만 | 각 규칙에 **평일 17~19시 추가근무** 후보 추가, 승인 시 근무달력에 저장 |
| 지연 4시간 57분은 어떤 순서로도 안 줄었음 | 추가근무 2시간으로 **2시간 57분**까지 줄었지만 여전히 긴급 |
| Pico 단말 계획 | **미연동**. 같은 API를 쓰는 가상 단말로 대체 |

## 2분: 모의 공장과 용어

- **3 LOT × 30대 = 90대.** 공정: 테이핑 → 외부 피드 본딩(외부) → 일반 조립 → 튜닝(25분/대) → 마무리 조립 → 최종 성능시험(30분/대) → 출하검사.
- **병목**: 튜닝장비 1대, 시험장비 1대. 작업자 2명. 근무 평일 9~17시.
- **Gate(출하검사 예정 시작)**: LOT-001 10/23 09:00, LOT-003 10/28 09:00, LOT-002 11/06 09:00.
- **고객 납기**: LOT-001 10/29 17:00, LOT-003 11/04, LOT-002 11/12.
- **Forecast**: 완료된 Unit의 실제 속도(3개 미만이면 표준시간)로 남은 작업을 자원·근무시간 안에 배치해 완료 시각을 예측.
- **긴급**: 예측 완료가 Gate보다 늦음(여유 ≤ 0).
- **출하검사 진입 지연**(핵심 지표): 생산 완료 − Gate. 중간발표의 4시간 57분이 이것.
- **최종 납기 지각**: 출하검사(시작일 포함 3근무일, 셋째 날 17시 종료) 후 출하가 고객 납기보다 늦은 시간. 두 지표는 다른 것.

## 2분: 재계획과 추가근무

1. 긴급이면 4가지 규칙으로 남은 작업을 다시 배치한 후보를 만든다.
   - FCFS 먼저 들어온 LOT / EDD Gate가 빠른 LOT / Slack 여유가 적은 LOT / CR 긴급도 비율이 높은 LOT 우선.
2. 추가근무를 켜면 규칙마다 "17~19시를 연" 후보를 하나 더 만든다. 실제로 쓰지 않는 날은 뺀다.
3. **순위**: 지연 LOT 수 → 총 지연시간 → 추가 가동시간 → 계획 변경량. 지연이 같으면 추가근무가 적은 쪽이 이긴다.
4. 관리자가 승인해야만 반영된다. 승인하면 계획 버전이 올라가고(v1 → v2), 추가근무는 근무달력에 저장되어 Forecast와 현장이 함께 쓴다.

**시연 숫자**: U030에 480분 입력 → LOT-001이 Gate보다 297분(4시간 57분) 늦음. 순서만 바꾸면 297분 그대로(FCFS는 549분). 추가근무안은 10/22에 2시간 열어 177분(2시간 57분). 승인 후 v2, 여전히 긴급.

## 2분: 실험과 결과

**설계**: 시작은 10/22 13:00, 기준계획은 접수순(LOT-001 → 002 → 003). 그래서 Gate가 빠른 LOT-003이 LOT-002 뒤에 있는, **일부러 만든 충돌 상황**입니다. 조건은 정상 / 작업시간 +20% / 작업정지·재작업. 같은 seed는 모든 구성이 같은 실제 작업시간을 받습니다(공정한 비교).

**외울 숫자 (출하검사 진입 지연 평균, 분)**

| | 정상 | +20% | 작업정지·재작업 |
|---|---|---|---|
| 계획 유지 | 190 | 1,523 | 2,433 |
| EDD | 0 (30/30) | 0 (30/30) | 14.6 (30회 중 5회 지연 남음) |
| FCFS | 189.5 | 1,476 | 2,329 |

- **추가근무 효과**: 작업정지 조건 CR 117 → 72분, 정상 조건 FCFS 190 → 118분.
- **추가근무 낭비**: 정상 조건 EDD는 이미 0인데 추가근무를 켜면 평균 108분을 씀(30회 중 27회). 결정 시점 예측이 비관적이라서 → **한계로 보고**.
- **최종 납기 지각**: 810회 모두 0. 이 데모는 납기 여유가 커서, 지켜야 하는 선은 Gate였다.
- 공장 규칙 위반 0, 실패 0, 테스트 384개 통과(Python 3.11·3.13).

## 1분: 숨기지 않는 것들

- **Pico 단말 미연동.**
- 작업시간 분포·교란 확률은 **가정값**(실제 공장 데이터 아님).
- 시작 상태는 재계획이 효과를 내도록 **의도적으로 만든 상황**이라 일반적인 성능 수치가 아님.
- 첫 본실험에서 810회 중 **3회 실패**(17시 정각 재계획 버그) → 수정 후 재실행, 실패 기록은 저장소에 남김.
- 예측이 비관적이면 **불필요한 추가근무**를 고름.
- 출하검사 자체의 대기·불합격, HOLD/RESUME 이벤트, 인증·권한은 범위 밖.
