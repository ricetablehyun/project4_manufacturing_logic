# 공프4 기말 — 10분 만에 이해하기 (기준본)

발표 전에 한 번 읽으면 질문에 발표와 같은 논리로 답할 수 있도록 정리했습니다. 장 번호는 `공프4_기말발표_PPT.pptx`(28장) 기준입니다.

## 1분: 한 문장 요약

**현장 실적이 들어오면 출하검사 약속 시각(Gate)에 늦을지 다시 계산하고, 늦을 것 같으면 순서를 바꾼 계획(필요하면 추가근무 포함)을 제안하며, 관리자가 고른 계획이 다시 현장 작업지시로 내려가는 시스템을 만들고, 가상 현장에서 810번 돌려 효과를 확인했다.**

## 1분: 쉬운 말 ↔ 용어

| 발표에서 먼저 쓰는 말 | 용어 |
|---|---|
| 제품 30개 묶음 / 제품 하나 | LOT / Unit |
| 출하검사에 들어가기로 약속한 시각 | Gate |
| 제품 하나를 만드는 데 걸리는 평균 시간 | Pace |
| 장비·작업자·근무시간 한계를 지키며 일정 채우기 | 유한용량 스케줄링 |
| 그렇게 나온 예상 완료 시각 | Forecast |
| 한 대뿐이라 줄이 생기는 장비 | 병목 (튜닝 장비, 최종 성능시험 장비) |
| 계획 → 현장 작업 → 실적 → 다시 계획으로 닫힌 고리 | 폐루프 |
| 먼저 들어온 묶음부터 / 약속이 빠른 묶음부터 / 여유가 적은 묶음부터 / 남은 시간 대비 일이 많은 묶음부터 | FCFS / EDD / Slack / CR |
| 평소 / 느린 날 / 돌발 지연·재작업 | NORMAL / SLOW / STOPPAGE_REWORK (보고서: 정상 / 작업시간 +20% / 작업정지·재작업) |

## 2분: 시연 이야기 (1~14장)

1. 10/22 13:17, 작업자가 U030(LOT-001의 30번째 제품)에 "튜닝 480분 더"를 입력한다.
2. Forecast가 다시 계산된다. 튜닝 장비는 한 대, 근무는 17시까지라 **오늘 3시간 43분 + 내일 4시간 17분 → 10/23 13:17 튜닝 끝, 마무리·시험 40분 → 13:57**. Gate 09:00보다 **4시간 57분(297분)** 늦어 긴급.
3. 늦어진 게 U030 자체라 순서를 바꿔도 그대로(EDD·Slack·CR 297분, FCFS는 다른 묶음까지 늦어 합계 549분).
4. 추가근무 후보(평일 17~19시)를 켜면 10/22 저녁 2시간으로 **2시간 57분(177분)**, 공동 1위. Gate 전 저녁이 하루뿐이라 여전히 긴급.
5. 관리자가 EDD + 추가근무안을 승인 → 계획 v2, 근무달력에 추가근무 저장. 시연 영상(14장, 약 60초)에서 현장 작업지시가 "LOT-003 마무리 조립" → "LOT-003 최종 성능시험"으로 바뀌고, 17시 이후 추가근무 작업이 생기는 것을 보여 준다. 현장이 그 지시를 따르는지는 영상이 아니라 실험·테스트로 확인했다.

**주의**: 12~13장과 22~23장의 시각은 모두 시스템이 계산한 **예상(Forecast)**이다. 297분은 시연 한 장면의 예측이고, 실험의 190분 등은 별도 실험(10/22 13:00 시작)의 30회 평균이다.

**Forecast 계산(6장)**: ① Pace = 끝난 Unit 3개 이상이면 실제 평균, 아니면 표준시간 ② 남은 일 = 남은 Unit 수 × Pace(작업 중인 제품이 길어지면 작업자에게 남은 시간을 물음) ③ 장비·작업자·근무시간 안에 채움.

**후보 순위(11장)**: 늦는 묶음 수 → 총 지연시간 → 추가근무 시간 → 계획 변경량. 앞이 같을 때만 다음을 본다.

## 2분: 실험 (15~25장)

- **왜**: 한 번 잘 된 건 우연일 수 있어서. 3조건 × 9방법 × 30회 = 810회.
- **9방법** = 계획 유지 1 + 규칙 4 × 추가근무 끔·켬 2.
- **같은 번호(seed)** = 모든 방법이 같은 실제 작업시간을 받는다 → 같은 시험지 비교.
- **누가 일하고 승인했나(16장)**: 가상 현장(시스템이 모르는 실제 작업시간)과 가상 관리자(긴급일 때만, 정해진 규칙의 후보, 추가근무안은 순위가 더 좋을 때만, **사람과 같은 승인 API**). 실제 화면은 사람이 승인.
- **출발점(17~18장)**: 10/22 13:00, 계획은 접수순. 약속이 빠른 LOT-003(10/28)이 LOT-002(11/06) 뒤 → 일부러 만든 충돌. EDD는 LOT-003을 앞으로.

**외울 숫자 (출하검사 진입 지연 평균, 분)**

| | 평소 | 느린 날 | 돌발 지연·재작업 |
|---|---|---|---|
| 계획 유지 | 190 | 1,523 | 2,433 |
| EDD | 0 (늦음 0/30) | 0 (0/30) | 14.6 (늦음 5/30) |

- 값은 한 번 실행에서 늦은 묶음들의 지연을 더한 값의 30회 평균. '늦음'은 고객 납기가 아니라 출하검사 약속(Gate) 기준.
- 간트(22~23장, 예상 일정): 막대는 첫 제품 시작~마지막 제품 종료 범위(대기·밤 포함, 장비 연속 사용 아님). 계획 유지면 LOT-003 최종시험 10/28 12:15 완료로 약속 09:00 초과, EDD면 10/23 15:30 완료.
- 추가근무(25장): 돌발 지연·재작업 CR 117 → 72분(추가 가동 382분 = 여러 날 합계, 하루 한도 120분), 평소 FCFS 189 → 118분. **평소 EDD는 이미 0인데 평균 108분 추가 가동 발생**(30회 중 27회). 108분은 관찰, 원인(결정 시점 예측이 비관적)은 **추정**. '부담'은 금액이 아니라 추가 가동시간.
- 고객 납기 지각: 출하검사 3근무일 **가정하에** 810회 모두 0(납기 준수율 100%라 방법 간 차이가 안 보여 주지표를 출하검사 진입 지연으로 바꿈). 평균 완료시간은 보조 결과: 계획 유지 18.7/22.5/26.1시간 → EDD 12.7/15.2/18.8시간.
- 그래도 재계획이 필요한 이유: 출하검사가 밀리면 검사 일정이 밀리고, 납기 여유가 적은 주문에선 바로 지각이 된다.
- 검증(26장): 두 종류. 테스트 384개(계산 하나하나, Python 3.11·3.13)와 810회 실험(전체가 끝까지 도는지), 공장 규칙 위반 0, 첫 실행 3회 실패(17시 정각 버그) → 수정 후 전부 성공, 기록 보존.

## 1분: 숨기지 않는 것들 (27장)

- Pico 단말 미연동(TCP 테스트는 localhost, Wi-Fi 아님).
- 작업시간 분포·교란 확률은 가정값. σ=0.15는 ±15% 한계가 아님.
- 돌발 지연은 작업시간 240분 연장 모델. HOLD/RESUME API는 구현·테스트했지만 실험에선 안 씀.
- 출하검사 자체의 대기·불합격은 범위 밖(3근무일 가정).
- 의도적으로 만든 충돌이라 EDD가 어디서나 최선이라고 하지 않음. 결과는 "지연을 크게 줄였다"(없앴다 아님).
