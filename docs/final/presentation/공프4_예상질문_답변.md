# 공프4 기말발표 예상 질문과 답변 (기준본)

답변은 30초 안쪽으로 말할 수 있게 썼고, 발표에서 쓴 쉬운 설명과 같은 논리로 맞췄습니다. 발표에서 조건 이름은 평소·느린 날·돌발 지연·재작업으로 불렀고, 원자료의 NORMAL·SLOW·STOPPAGE_REWORK(보고서의 정상·작업시간 +20%·작업정지·재작업)와 같습니다. 시연의 297분(한 장면의 예측)과 실험의 190분 등(810회 평균)은 서로 다른 숫자입니다. 숫자 근거는 `experiments/main30/summary.csv`, 기능 근거는 `docs/verification.md`의 테스트입니다. **굵은 글씨**가 핵심 한 문장입니다.

## A. 폐루프와 시스템

**Q1. "폐루프"라고 했는데, 실제 현장이 아니라 시뮬레이터 아닌가요?**
**맞습니다. 현장은 가상 현장 시뮬레이터이고, 폐루프는 시뮬레이터와 시스템 사이에서 확인한 것입니다.** 다만 시뮬레이터는 시스템 내부를 직접 건드리지 않고 실제 단말과 같은 HTTP API만 씁니다. 시스템이 모르는 실제 작업시간으로 움직이고, 작업자 추정에도 오차를 넣었습니다. 같은 컴퓨터(localhost)의 실제 TCP 소켓으로 띄운 서버에서도 같은 루프가 돈다는 테스트가 있습니다. 다만 Pico의 Wi-Fi 통신을 검증한 것은 아닙니다.

**Q2. 승인이 현장을 바꾼다는 건 어떻게 확인했나요?**
**같은 현장 조건에서 승인 전후의 실제 완료 순서가 달라지는지를 테스트로 확인했습니다**(`test_approval_changes_the_executed_order`). 또 실제 작업시간을 표준시간과 같게 두면 현장 결과가 승인 시점의 Forecast와 정확히 같아지는지도 확인했습니다. 이 둘이 맞으면 "계획대로 현장이 움직인다"고 말할 수 있다고 봤습니다.

**Q3. Pico 단말은 왜 연동하지 못했나요?**
**우선순위를 폐루프와 실험 검증에 두었고, 단말 펌웨어는 일정 안에 하지 못했습니다.** 단말이 보낼 실적 API와 받을 작업지시 API는 구현·테스트되어 있어서, 단말은 이 API를 호출하는 클라이언트만 만들면 됩니다. 하지만 하드웨어에서 확인하지 않았으므로 "연동 가능"이 아니라 "미연동"으로 보고합니다.

**Q4. Forecast는 어떻게 계산하나요?**
완료된 Unit 실적으로 LOT × 공정 속도(Pace)를 구하고(표본 3개 미만이면 표준시간 사용), 남은 작업을 작업자 2명·튜닝장비·시험장비·근무시간 제약 안에서 이벤트 단위로 배치합니다. **마지막 최종 성능시험 완료 예상과 출하검사 Gate 예정 시각의 차이가 여유이고, 0 이하면 긴급입니다.** 작업자가 잔여시간을 입력하면 그 작업은 Pace 대신 입력값을 씁니다.

**Q5. 재계획 후보의 순위는 어떻게 정하나요?**
**지연 LOT 수 → 총 지연시간 → 추가 가동시간 → 계획 변경량 순서로 비교합니다.** 앞 기준이 같을 때만 뒤 기준을 봅니다. 그래서 지연이 같으면 추가근무가 적은 안이 앞섭니다. 시연에서 FCFS + 추가근무도 지연은 2시간 57분이었지만 6시간을 써서 공동 1위(2시간)보다 뒤였습니다.

**Q6. 4가지 규칙 말고 최적화(MILP 등)는 왜 안 썼나요?**
현장 관리자가 이해하고 고를 수 있는 규칙 기반 후보 비교를 목표로 했습니다. **최적해를 보장하지 않는다는 것은 한계입니다.** 실험에서도 규칙에 따라 결과 차이가 컸고(예: 돌발 지연·재작업 조건 EDD 14.6분, CR 117.1분), 최적화 비교는 향후 과제입니다.

**Q7. 승인하지 않으면 어떻게 되나요?**
자동 적용은 없습니다. 관리자가 승인해야 새 계획 버전이 생기고 작업지시가 바뀝니다. 실험의 KEEP 구성이 바로 "승인하지 않는" 경우입니다.

## B. 실험

**Q8. 기준계획을 일부러 접수순으로 둔 건 결과를 유리하게 만든 것 아닌가요?**
**네, 재계획 효과를 보기 위해 의도적으로 만든 충돌 상황이고 발표·보고서에 그렇게 밝혔습니다.** 출하검사가 빠른 LOT-003이 LOT-002 뒤에 있으므로 순서를 바꾸면 좋아지는 상황입니다. 그래서 "재계획이 일반적으로 지연을 X% 줄인다"가 아니라, "이런 상황에서 시스템이 그 문제를 찾아 고치고, 교란이 있어도 효과가 유지되는가"를 확인한 실험입니다.

**Q9. 30번이면 충분한가요?**
구성당 30 seed이고, 평균과 95% 신뢰구간(t분포)을 함께 보였습니다. 주요 비교(KEEP 대비 EDD)는 신뢰구간이 0과 멀리 떨어져 있습니다. 또 공통 난수를 써서 같은 seed끼리 짝지어 비교했기 때문에 차이의 분산이 작습니다. 다만 Slack 돌발 지연·재작업 조건처럼 한 번의 큰 지연(약 1,600분)이 평균을 끌어올리는 경우는 신뢰구간이 넓습니다(90.8 ± 110.3분).

**Q10. 공통 난수(같은 seed)가 왜 필요한가요?**
**같은 seed면 모든 구성이 같은 실제 작업시간과 같은 불합격을 받게 해서, 차이가 운이 아니라 재계획 방법에서 오게 했습니다.**

**Q11. 작업시간 분포와 교란 확률은 어디서 왔나요?**
**실제 공장 데이터가 아니라 가정값입니다.** 작업시간은 표준시간에 로그정규 잡음(σ=0.15)을 곱합니다. σ=0.15는 "±15% 안"이라는 뜻이 아니고, 약 3분의 2가 ±15% 안에 들며 그 밖으로도 벗어납니다. 그 밖에 작업자 추정 오차 σ=0.2, 돌발 지연은 작업 시도의 3%에 240분, 최종 성능시험 불합격 8%입니다. 결과의 절대 수치보다 같은 조건에서의 비교로 읽어 달라고 말씀드리고, 실제 데이터 보정은 향후 과제로 두었습니다.

**Q12. FCFS가 계획 유지와 거의 같은 건 이상하지 않나요?**
기준계획 자체가 접수순(FCFS)이라 예상된 결과입니다. 평소 조건 짝지은 차이가 −0.9 ± 1.6분입니다. **순서를 바꾸지 않으면 결과도 바뀌지 않는다는 대조군 역할**을 합니다.

**Q13. EDD가 왜 좋았나요? 항상 좋은 건가요?**
이 데모의 지연은 출하검사가 빠른 LOT-003이 접수순 때문에 LOT-002 뒤에 놓여 병목 장비(튜닝·시험)를 늦게 받는 데서 생깁니다. EDD는 Gate가 빠른 LOT부터 병목 장비를 쓰게 하므로 바로 이 원인을 없앱니다(간트차트 슬라이드). 이 실험 조건에서는 가장 좋았지만, 돌발 지연·재작업 조건에서 30회 중 5회는 지연이 남았습니다. **이 데모의 지연이 "출하검사 일정 순서" 문제였기 때문에 EDD가 잘 맞은 것**이고, 다른 상황에서도 EDD가 최선이라고 일반화하지 않습니다.

**Q14. CR은 왜 결과가 나쁜가요?**
CR은 실행당 평균 3.2~4.3회 승인하며 계획을 자주 바꿨고, 평소 조건에서도 평균 34.3분 지연이 남았습니다. 원인을 정밀하게 분석하지는 않았습니다. 긴급도 비율이 남은 작업량에 민감해서 LOT 간 순서가 자주 뒤집히는 것으로 추정하지만, **검증하지 않은 추정**입니다.

## C. 추가근무

**Q15. 평소 조건 EDD에서 쓸모없는 추가근무를 108분 연 건 버그 아닌가요?**
**관찰한 것은 "지연이 이미 0인데 평균 108분 추가 가동이 생겼다(30회 중 27회 사용)"는 사실입니다.** 원인은 결정하는 순간의 Forecast가 실제보다 비관적이라, 지연을 줄여 보이는 추가근무안이 순위에서 앞섰기 때문으로 **추정**합니다. 이 원인을 따로 실험해 확인하지는 않았으므로, 버그인지 설계상 한계인지 단정하지 않고 한계로 보고합니다. 예측 보정이나 추가 가동시간을 순위에 더 무겁게 반영하는 것이 개선 방향입니다.

**Q16. 추가 가동시간은 어떻게 셉니까?**
추가근무를 쓴 날의 17시부터 그 창 안 마지막 작업 종료까지입니다. **중간 대기시간도 포함합니다.** 사람과 설비가 남아 있어야 하기 때문입니다. 쓰지 않는 날은 창에서 빼서 계산합니다.

**Q17. 시연에서 추가근무를 해도 왜 긴급으로 남나요?**
허용한 추가근무는 평일 17~19시이고, LOT-001의 약속(10/23 09:00) 전에 쓸 수 있는 저녁은 10/22 하루뿐이라 4시간 57분 지연 중 2시간만 줄였습니다(→ 2시간 57분). 계산은 PPT 12·13장: 튜닝 480분 = 오늘 3시간 43분 + 내일 4시간 17분, 끝나는 13:17에 마무리·시험 40분을 더해 13:57(약속보다 4시간 57분 늦음), 추가근무 2시간이면 11:57(2시간 57분 늦음). **추가근무로 해결됐다가 아니라, 줄었지만 남는다**가 정확한 결과입니다.

## D. 지표

**Q18. 출하검사 진입 지연과 최종 납기 지각이 왜 다른가요?**
출하검사 진입 지연은 생산 완료가 출하검사 시작(Gate)보다 늦은 시간이고, 최종 납기 지각은 출하검사(시작일 포함 3근무일)를 마치고 출하한 시각이 고객 납기보다 늦은 시간입니다. **중간발표의 4시간 57분은 앞의 것이고 고객 납기 지각이 아닙니다.** 이 데모는 고객 납기에 여유가 있어 출하검사가 시작일 포함 3근무일에 끝난다는 **가정하에서** 810회 모두 최종 납기 지각이 0이었습니다(가장 빠듯한 경우 납기 당일 17시 출하).

**Q19. 그럼 최종 납기 지각이 0인데 재계획이 의미가 있나요?**
현장에서는 출하검사 시작이 늦으면 검사 인력·설비 일정이 밀리므로 Gate 자체가 지켜야 할 선이라고 봤습니다. 출하검사가 밀리면 검사 인력·설비 일정이 같이 밀리고, 고객 납기 여유가 적은 주문에서는 그대로 지각이 됩니다. 그래서 이 시스템은 고객 납기보다 앞선 공장 안의 약속(Gate)을 지키는 데 초점을 뒀습니다. 다만 **이 데모에서 고객 납기 기준의 이득은 보이지 않았다**는 점은 그대로 인정합니다. 출하검사 자체의 대기·불합격은 모델링하지 않았습니다.

## E. 검증과 품질

**Q20. 실험 중 실패한 3번은 무엇이었나요?**
17시 정각에 재계획이 일어날 때, 진행 중 작업이 그 시각에 바로 이어진다고 가정한 코드 때문에 서버가 409를 돌려줬습니다. **다음 근무 시작(다음 날 9시)에 이어지도록 고치고 회귀 테스트를 추가한 뒤 3번을 다시 돌려 모두 성공했고, 실패 기록은 지우지 않고 남겼습니다.**

**Q21. 공장 규칙 위반 0건은 무엇을 검사한 건가요?**
가상 현장이 매 작업 시작마다 같은 작업 중복 시작, 자원 용량 초과, 선행 공정 완료 전 시작, 근무시간 밖 시작을 검사합니다. 810회 모두 0건이었습니다.

**Q22. 384개 테스트는 무엇을 보장하나요?**
계산 로직 단위 테스트, API 통합 테스트, 중간발표 수치 회귀 테스트(4시간 57분, 297분, 549분이 그대로 나오는지), 폐루프·추가근무 테스트입니다. Python 3.11과 3.13 두 버전에서 GitHub Actions로 돕니다. **테스트가 실제 현장 정확도를 보장하지는 않습니다.**

## G. 검토에서 나온 추가 질문 (v2)

**Q23. 810회를 돌렸다는 건 어떤 검증인가요?**
**한 번의 시연이 우연이 아니라는 것, 그리고 교란이 있어도 폐루프가 끝까지 돌고 효과가 유지된다는 것을 보인 검증입니다.** 3가지 교란 조건 × 9가지 재계획 구성 × 30 seed이고, 같은 seed는 모든 구성에 같은 실제 작업시간을 줘서 차이가 재계획 방법에서만 오게 했습니다. 실제 공장 성능을 예측한 것은 아닙니다. 작업시간 분포가 가정값이기 때문입니다.

**Q24. 돌발 지연·재작업 조건은 실제 HOLD/RESUME 이벤트를 쓴 건가요?**
**아닙니다.** 실험의 돌발 지연은 작업 시도의 3%에 작업시간 240분을 더하는 모델입니다. HOLD/RESUME API는 구현·테스트되어 있지만 실험에서는 보내지 않았습니다.

**Q25. 그래프 숫자가 작아 안 보이는데 핵심이 뭔가요?**
계획 유지 평균 190 / 1,523 / 2,433분 → EDD 0 / 0 / 14.6분(돌발 지연·재작업 조건 30회 중 5회 지연 남음). 추가근무는 돌발 지연·재작업 CR 117 → 72분, 평소 FCFS 189 → 118분, 하지만 평소 EDD는 0분인데도 평균 108분의 추가 가동시간 발생.

## H. 기준본(모핑) 발표에서 새로 나올 수 있는 질문

**Q26. 810번을 사람이 직접 승인했나요?**
**아닙니다. 실험에서는 가상 관리자 프로그램이 승인했고, 실제 화면에서는 사람이 직접 고르고 승인합니다.** 가상 관리자는 시스템이 긴급이라고 할 때만 후보를 요청하고, 구성에 정해진 규칙(예: EDD)의 후보를 고릅니다. 추가근무가 켜진 구성에서는 같은 규칙의 추가근무안이 같은 순위 기준(D029)으로 더 나을 때만 그것을 고릅니다. 승인은 관리자 화면과 같은 승인 API를 호출합니다(`src/production_control/sim/manager.py`). 그래서 승인 이후 계획 버전·작업지시가 만들어지는 경로는 같습니다. 다만 현장도 가상 현장이므로, 실제 공장 운영과 같다고까지는 말하지 않습니다.

**Q27. 시연에서 순서를 바꿔도 왜 297분이 그대로였나요?**
**늦어진 것이 U030 한 제품 자체이기 때문입니다.** U030은 튜닝이 480분 남았고 튜닝 장비는 한 대라, 다른 묶음 순서를 어떻게 바꿔도 U030이 끝나는 시각(10/23 13:17, 이후 마무리·시험 40분)은 같습니다. FCFS가 549분인 것은 LOT-001의 297분에 다른 묶음의 지연이 더해진 합계입니다.

**Q28. Pace는 정확히 어떻게 정하나요?**
LOT × 공정마다, 끝난 Unit이 3개 이상이면 그 실제 작업시간의 평균, 3개 미만이면 사람이 정한 표준시간입니다(`core/pace_estimator.py`). 남은 일 = 남은 Unit 수 × Pace이고, 작업 중인 Unit이 Pace 예산을 넘으면 작업자에게 남은 시간을 물어 그 값을 씁니다.

**Q29. 슬라이드가 움직이는(모핑) 부분이 안 보이면요?**
모핑은 PowerPoint 2019 이상과 Microsoft 365에서만 움직이고, 다른 프로그램에서는 페이드로 넘어갑니다. 내용은 정지 화면으로도 모두 읽히게 만들었습니다. 810개 점이 움직이는 장면이 버벅이면 같은 내용의 백업판(점이 제자리에서 색만 바뀜)을 씁니다.

**Q30. 시연의 297분과 실험의 190분은 같은 상황인가요?**
**아닙니다.** 297분은 시연 장면(10/22 13:17, U030에 480분 입력) 한 번에서 계산한 예상 지연입니다. 190분은 별도 반복 실험(10/22 13:00 시작, 접수순 계획 유지, 평소 조건)의 30회 평균입니다. 시작 상태와 원인이 다릅니다. 시연은 U030 한 제품이 길어진 상황이고, 실험은 출하검사 약속이 빠른 LOT-003이 뒤에 서 있는 순서 충돌 상황입니다.

**Q31. 간트차트에서 같은 장비를 쓰는 막대가 겹쳐 보이는데요?**
**막대는 그 공정의 첫 제품 시작부터 마지막 제품 종료까지의 범위라서, 중간 대기와 밤이 들어 있습니다.** 장비를 그동안 계속 쓴다는 뜻이 아닙니다. 장비 한 대에 한 제품만 들어가는지는 가상 현장이 매 작업 시작마다 검사했고, 810회 모두 위반 0건이었습니다.

**Q32. 추가근무는 하루 최대 2시간인데 382분은 어떻게 나왔나요?**
**382분은 한 번 실행 동안 여러 날에 쓴 추가 가동시간을 모두 더한 값의 30회 평균입니다.** 하루 한도는 17~19시 120분이고, 실행 하나가 여러 날에 걸치므로 합계는 120분을 넘을 수 있습니다. 여기서 "부담"은 금액이 아니라 추가로 공장을 돌린 시간입니다.

**Q33. 계획서의 처음 지표(납기 준수율, 평균 완료시간)는 어떻게 됐나요?**
**납기 준수율(고객 납기 기준)은 810회 모두 100%라서 방법 사이 차이를 보여 주지 못했습니다.** 그래서 차이가 드러나는 출하검사 진입 지연을 주지표로 바꿨습니다. 평균 완료시간(시작부터 LOT 생산 완료까지 근무시간, LOT 평균)은 보조 결과로 남겼습니다. 계획 유지 18.7 / 22.5 / 26.1시간, EDD 12.7 / 15.2 / 18.8시간(평소 / 느린 날 / 돌발 지연·재작업)입니다(`experiments/main30/summary.csv`).
